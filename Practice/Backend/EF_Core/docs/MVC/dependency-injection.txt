Dependency Injection (DI)

  - DI is a technique for achieving loose coupling between object and their dependencies.
  - Loose coupling is a software design principle where components or modules of a system
    are designed to be largely independent of each other. Like for example, the DB 
    Context injecting the _mapper.

  - DI is also considered as a software design pattern and a technique for achieving 
    inversion of control (IoC) between classes and their dependencies. An object that 
    another object depend on. For example, the Controller depends on the DbContext.
    
  - DI increases maintainability and testability.
  - DI is built into ASP.NET Core.
  - DI manages the life time of and dependencies of services used throughout the 
    application.
  - Instead of instantiating a new object of a class, these dependencies are passed to 
    that class (as parameters to the constructor). This a allows for a greater 
    flexibility in a way objects are created and managed, and easier testing of 
    individual components.

  - DI container is responsible for creating and managing instances when the application
    starts.

  Scoped vs Transient bs Singleton
    - AddScoped 
      - Created once per request.
      - EF Core is automatically registered as an AddScoped service.
      - Best used for database operations. Connects once, and maintain that connection
        for the lifetime of that request.
    - AddTransient 
      - Services are created each time they are requested.
      - This lifetime works best for lightweight stateless services.
    - AddSingelton
      - Created the first time they are requested and then every subsequent request
        will use the same instance.
      - Best used for state change and keep track of it.  

 Why use DI?
  - Objects are disposed of automatically.
    - Manual instantiating requires more deliberate effort to prevent memory leaks. 
  - Easier long-term maintenance of application code.
  - Keeps the codebase SOLID - Dependency Inversion Principle (DIP)
    - High-level modules should not depend on low-level modules; both should 
      depend on abstractions like interfaces or abstract classes.   
    - This principle promotes decoupling by inverting the direction of dependency,
      making code more flexible, maintainable, and testable.
    - High-level components (business logic) and low-level components (e.g., 
      database access) should both rely on an abstraction, which is then implemented 
      by the low-level component. 
      - Good for static resources, like a file that has to be available all the time.
